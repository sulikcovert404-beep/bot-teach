## Finding

`TenantAuthoritySnapshotV1` is qualified source but has no application call site. It does not currently establish request context or authorize a route. The repository therefore still has multiple live authorization seams: a canonical `UserTenantMembership` resolver, a `PrincipalAuthoritySnapshot` module that is not wired to routes, legacy `TeacherProfile` and `SchoolAdminMembership` checks, database-owned membership/enrollment functions, direct client-selected tenant/classroom contexts, and some tenant-labelled operational/demo data.

The highest-risk convergence targets are the six `/api/v1/admin` tenant query endpoints, `/api/v1/sources/search`, optional tenant/classroom/assignment context at `/api/v1/tutor/answer`, and persistent teacher endpoints that use `TeacherProfile` without the canonical membership resolver. The six admin routes pass an omitted tenant through for `SUPER_ADMIN`; their query filters are conditional, so omission can produce platform-wide result sets. The source search route selects a classroom from a request parameter and uses legacy profile/membership rows before putting that classroom's tenant into the RLS GUC. The tutor route checks a complete request-provided context against classroom/assignment/student joins but does not resolve the current canonical tenant or establish RLS context before retrieval.

Some paths already use `public.resolve_tenant` and exact-one canonical membership semantics, notably student assignment/exam context and the class-enrollment SQL functions. Those paths still authenticate through JWT subject/role dependencies rather than composing the two qualified fresh snapshots. Several teacher routes mix canonical tenant resolution with legacy profile ownership checks. This is not a basis for bulk rewiring: preserve each endpoint's present business behavior until the unresolved `SUPER_ADMIN`, legacy compatibility, and client contract questions are decided.

## Method and coverage boundary

The audit is bound to the exact A12TIP source SHA. It inspected router declarations and mounts in `app/main.py`, endpoint bodies and dependencies, tenant-related helpers and services, model definitions, relevant migration SQL, MAOS Python/SQL paths, and matching tests. Static searches included tenant IDs, school/classroom IDs, membership/profile models, resolver/context functions, GUC names, and MAOS tenant APIs. The report lists every application entry point found that resolves, accepts, propagates, or stores tenant identity, grouped by common authority seam; non-tenant platform/control endpoints are not presented as tenant routes merely because they require an admin role.

This is a source audit, not a live route invocation, deployed-schema inspection, dynamic call-graph proof, or production data audit. Generated routes, plugin-loaded code, out-of-repository workers, and external clients cannot be established from this checkout. `app/main.py` showed no separate tenant scheduler/worker registration. Service and repository helpers called by the listed handlers are included below where their tenant behavior is material.

## Route and entry-point inventory

Classification values used here: **CANONICAL** means the handler/service reaches canonical membership authority; **LEGACY** means profile or legacy membership is decisive; **DERIVED** means tenant comes from another selected object or an assumed relation; **PROPAGATION_ONLY** means context is passed to SQL/RLS but not authorized there; **UNSAFE_SELECTOR** means client-supplied tenant/classroom can select scope before canonical proof; **NO_TENANT_AUTH_REQUIRED** means source inspection showed platform-global, user-keyed, static/demo, or non-tenant behavior rather than a tenant authorization operation. A mixed row names both mechanisms instead of hiding the weaker one.

## High-priority findings
